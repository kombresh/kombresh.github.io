方法說明

兩條流水線怎麼組起來的、我們用什麼證明它沒有在編造，以及哪些事情它做不到。 最後一節是這一頁最重要的部分。

兩邊的架構

動態端 —— Speakeasy 模擬 + LLM 環境偽裝

樣本的機器碼跑在模擬器的虛擬 CPU 上，Windows API 由 Python handler 接手。 樣本從頭到尾沒有真的 socket、沒有真的檔案系統。

  1. 內圈（每次呼叫）：攔截所有 API 呼叫。有前例就照帳本回同一個答案， 沒有前例才問 LLM 要一個「像真機」的回傳值，其餘交回模擬器預設。
  2. 帳本：同一個問題，樣本每次都得到同一個答案 —— 反偵測的樣本常常問兩次比對。
  3. 外圈（每輪之間）：這一輪提早中止的話，把中止原因交給 LLM 修正環境剖繪， 然後整個重跑。最多五輪。
  4. 誠實護欄：這一輪如果依賴了「模擬器根本沒實作、值是我們合成的」API， 結果一律標成 inconclusive；LLM 端點掛掉或回不能用的內容時， 同時標 inconclusive 與 success = false。

LLM 只產生資料（環境剖繪的值、API 回傳計畫），不會去改流水線的程式碼。

靜態端 —— 規則式情報彙整

不執行樣本、不使用 LLM。八個工具各跑各的，結果彙整成一份固定 schema 的 JSON （static_intel/1）交給動態端。

  1. PE 結構（pefile）→ 架構、區段、匯入表、TLS callback、resource、overlay
  2. 加殼／編譯器偵測（DiE）→ packer / protector / linker
  3. 自動解殼與 PyInstaller 解包 → 只在適用時才跑
  4. 字串抽取（FLOSS）→ 含堆疊字串與執行期解密字串
  5. 能力標籤（capa）→ 能力與 ATT&CK 對應
  6. 自有規則比對（YARA，17 條）
  7. 反編譯（Ghidra headless）→ 只挑有碰到目標 API 的函式

推導出來的結論放 derived：檢測點清單、行為分類、加殼判定（一定附證據）、 C2 候選（含 benign 標記與 defanged 形式）、以及給動態端的模擬預算建議與理由。

主流程完全不用 LLM，是刻意的：可重現性與 LLM 的輸出不確定性互斥。 同一支樣本重跑，content_sha256 必須一致。

兩邊怎麼接

靜態端輸出的 suggested_budget_seconds、檢測點清單、以及 analysis_notes（例如「有 TLS callback，主要邏輯可能不在 entry point」） 就是要餵給動態端當起始條件的東西。 這一段已經跑過了（2026-07-30 的配對批次），但只接上其中兩項： 由檢測點派生的環境旗標與模擬預算。第三項 —— 依檢測點產生的建議 watchlist —— 沒有被套用， 因為那一批的執行條件是「不預先種 optional watchlist」。 所以第三組是對交接機制的部分驗證。

三組對照分別是什麼不要混淆

同一批樣本、同一台模擬器，差別只在「我們額外做了什麼」。 三組的語意必須分得開，不然「數字變大了」會被讀成「方法有效」。

① 純 Speakeasy

什麼都不做，直接把樣本丟進模擬器跑一次。

  • 沒有環境偽裝、沒有 LLM、沒有重跑
  • 模擬器碰到沒實作的 API 就中止
  • 這是對照組：反偵測的樣本會在這裡提早停下來

② ＋動態（mirage）

內圈由 LLM 即時捏造模擬器沒實作的 API 回傳值； 外圈每一輪依中止原因修訂環境剖繪後整個重跑。

  • 「跑得更深」是靠餵它一個更像真機的謊，不是靠看懂它
  • 只要有一個值是合成的，那一輪就標 inconclusive
  • 本批六支的 success 全部是 false、assisted 全部是 true

③ ＋動態＋靜態

先跑靜態流水線，把派生的環境旗標與模擬預算餵給動態端當起始條件。

  • 這一組是配對實驗：同六支、同一天、其他參數固定， 各跑一次「空 profile ＋ budget 60」與一次「靜態派生的 profile ＋ budget」
  • 能比的是它自己的兩欄，不是拿它去比 ② —— ② 是另一個批次、參數也不一樣
  • 只有 profile 與 budget 被套用；建議 watchlist 沒進場

為什麼第三組不畫在第二組的同一條軸上

因為那樣會把「批次與參數的差異」算成靜態情報的功勞。舉個實際的例子： 21080a1c 在第二組的最深一輪是 199,941 次呼叫，在第三組的 normal 欄是 88,254 次 —— 這兩個數字都是「同一個游標輪詢迴圈撞到 呼叫上限」，差別只在那一批的預算與上限設定。真正該比的是第三組自己的 88,254（空 profile）對 1,182（靜態派生的 profile）。

所以樣本詳情頁有兩張圖：第一張只放基線與第二組的每一輪，第二張是第三組的 normal 與 static-profile 逐輪並排。

第三組的分級是規則算出來的，不是看圖說故事

決定性改善：最深呼叫數變化 5 倍以上，或末輪相異 API 多 5 支以上。 小幅改善：變化 1.5 倍以上，或相異 API 多 2 支以上。 無明顯變化：門檻以下（含逐筆完全相同）。 門檻寫在 tools/build-data.py，改了門檻整站的分級會一起變 —— 不會出現「文字說有效、數字說沒差」的情況。

逐輪圖表怎麼讀四個容易讀錯的地方

  • 長條是「每輪各自的計數」，不是累積 迭代之間的 API 數不是單調遞增。本批最明顯的是 4ab7b0dd：13 → 28 → 14。第 3 輪 LLM 接管 ntdll 之後， 樣本走的是另一條更短的路。累積畫法在數字會下降時沒有意義， 所以圖表用每輪各自獨立的長條，旁邊標增減（+15 / −14）。 影響：所有樣本
  • 兩支用對數刻度，長條高度差 ≠ 倍數差 21080a1c（229 → 199,941）與 c6a4ffb8（325 → 6,797） 跨了兩到三個數量級。線性刻度會把小的那幾根壓成看不見的一條線， 所以這兩支的縱軸改成對數，並且在圖上用紅字標示 API（對數刻度）。看數字，不要看高度比例。 影響：動態端 · 本批 2 支
  • 最大的那個數字是失控迴圈，不是分析成果 21080a1c 第 2 輪的 199,941 次呼叫是 LLM 呼叫失敗（llm_call_failed）之後撞上模擬器 API 上限的結果 —— 呼叫幾乎全集中在同一個輪詢迴圈裡。 它不是「跑得比較深」，是「卡在原地卡了二十萬次」。 網站上那一輪的面板有紅色警語，不會讓它看起來像好結果。 影響：動態端 · 1 支 1 輪
  • 逐輪的「新增／消失 API」不是完整軌跡的差集 run 報告只帶最後一輪的完整 API 軌跡（api_trace_final）， 前面幾輪的完整序列沒有留存。所以面板上的「新增／消失」是就 外圈那一輪實際碰到的 API 名單算的 —— 攔截清單、合成回答、 LLM 宣告參數個數、派送例外、呼叫慣例修正、帶了字串引數的呼叫。 長條的高度（呼叫次數）才是完整計數。這個界線在每一個面板裡都寫著。 影響：動態端 · 全部
  • 停下來的理由多半是守衛，不是收斂 外圈有兩道守衛：no_behaviour_change（這一輪跟上一輪的軌跡指紋一樣） 與 no_progress（連續幾輪沒有推進）。本批六支裡有 四支是被這兩道停下來的。 「停了」不等於「跑完了」 —— 它只代表外圈判定再跑也不會不同。 影響：動態端 · 本批 4 支

三支驗證工具它們不能互相取代

「我覺得它跑對了」不是驗收標準。這三支各自把一個模糊的疑問變成可以印出來的結果， 而且各自有明確的盲區 —— 盲區才是重點。

工具 回答什麼 需要標準答案嗎 盲區
verify_groundtruth.py 抓得準不準 —— 算出 precision 與 recall 兩個數字。 關鍵設計是噪音基準線：一支什麼檢測都不做的負例， 它被偵測到的集合就是 CRT 啟動碼造成的噪音，其他樣本一律先扣掉這一層再算。 需要 只能用在自己寫的驗收樣本上。對真實惡意程式完全用不上 —— 真實樣本沒有標準答案。
validate_report.py 報告符不符合契約：schema、必填欄位、enum 範圍、 每個工具都有明確 status（沒有靜默的空欄位）、重跑的 content_sha256 是否一致。 不需要 假資料若連摘要一起重算，它會放行。 它證明的是「沒被事後改過」，不是「內容是真的」。
verify_evidence.py 報告說的東西是不是真的在檔案裡。刻意不重用流水線的程式碼： 自己開檔讀位元組、自己用 pefile 重新解析匯入表、自己重跑 YARA。 報告說抓到某個 C2，那個字串就必須真的在樣本的位元組裡。 不需要 不回答「有沒有漏抓」 —— 那需要外部參照。 也不看摘要，所以改掉數字但沒重算摘要的情況它抓不到。

兩個具體的漏網情境

  • 把假的 C2 塞進報告、並用專案自己的摘要函式重算 content_sha256 → validate_report 判定「未被竄改」，只有 verify_evidence 抓得到。
  • 改掉 derived 裡的某個數字但沒重算摘要 → verify_evidence 不看摘要，只有 validate_report 抓得到。

所以真實樣本的驗證要兩支都跑。

verify_evidence 自己出過四次誤報

它天生假設「報告裡的字串應該以明文存在於原始檔」。這個假設在 解殼後的檔案、zlib 壓進 overlay 的 PyInstaller 腳本、超長被截斷的字串、 以及執行期才解密的內容四種情況下都不成立，每一種都害它誤指流水線在編造。

第四次冤枉的正好是那批樣本裡最有價值的一筆情報（一個會加密自己 C2 的樣本）。 一個對最重要發現喊狼來了的檢查器，比沒有檢查器更糟。

誠實限制兩邊都做不到的事

這一節列的是已知會失敗的地方。工具的真實上限跟解析失敗是兩件事， 分不清楚的話，一份「什麼都沒抓到」的報告會被誤讀成「這支樣本很乾淨」。

  • VMProtect / PELock 解不開 被商業保護器包起來的樣本，靜態端解不開殼。反編譯 packer stub 沒有意義， 所以 Ghidra 那一步直接跳過，報告會標成證據不完整。 本批的 4ab7b0dd 就是這種：檢測點只剩 6 個、capa 只有 4 項 —— 那是「看不到」，不是「沒有」。 影響：靜態端 · 本批 1 支
  • PyArmor 之類的二次混淆 PyInstaller 打包的樣本可以解出 CArchive，但如果 PYZ 又被 PyArmor 混淆過， 模組名一個都取不回來，只剩 .pyd 這一層還看得見。 報告會把 obfuscator 標出來 —— 這是工具的真實上限，不是解析失敗， 兩者必須在報告裡分得開。 影響：靜態端
  • 執行期才解密的 C2，靜態抓不到；模擬走不到那裡也抓不到 C2 被加密藏在資料段時，明文掃描一定漏。字串抽取工具能還原一部分 （本站 787f2b0c 的 source=decoded 那一筆就是）， 但那條路徑只在解密邏輯夠簡單時走得通。真正的解法是讓樣本自己跑到解密那一行 —— 而那正是動態端在做的事，也正是純 Speakeasy 基線大多做不到的事。 影響：兩端
  • Speakeasy 的 API 覆蓋率是硬上限 模擬器沒實作到的 API 一碰到就中止。本批六支裡有兩支停在 kernel32.FlsGetValue2，各自只跑了 36 個 API 就結束 —— 那不是樣本的行為結束了，是模擬器走不下去了。 補值可以讓它繼續跑，但補出來的值無法驗證，所以那樣的結果必須標成 inconclusive，不能當成通過。 影響：動態端 · 本批 2 支
  • 只跑 DllMain 會漏掉大部分行為 DLL 的實際功能通常不放在 DllMain 裡。本站 787f2b0c 有對照： 只跑 DllMain 是 20 個 API，跑全部匯出函式是 58 個。 正式數據採用後者。這也代表任何「只看 entry point」的工具在 DLL 上都會嚴重低估。 影響：動態端 · 本批 1 支
  • content_sha256 防損壞，不防造假 它是不帶密鑰的自我摘要。任何人都可以改掉報告內容、 再用專案自己的函式重算一次摘要，閘門就會判定「未被竄改」。 它能證明的只有「這份 JSON 沒有在傳輸或編輯中損壞」。 要證明內容是真的，得靠 verify_evidence.py 那條獨立路徑。 影響：驗證層
  • 六支樣本不足以下任何統計結論 本站的數字是逐支樣本的觀察紀錄，不是量測結果。 「Speakeasy 對反偵測樣本的成功率」這種話，六支樣本說不出來。 影響：整體
  • 沒有做過網路隔離，只做到「未被原生執行」 動態分析期間 VM 是連通的 —— 要打 HTTPS 到 LLM 端點。 能說的只有「樣本的機器碼跑在虛擬 CPU 上、網路 API 由 handler 假造， 樣本從頭到尾沒有真的 socket」。不要宣稱做過網路隔離。 影響：動態端

這個站的資料怎麼產生的

tools/build-data.py 從兩個來源讀取、過濾、輸出到 data/，可以重跑。 這支腳本是安全邊界 —— 過濾在它裡面做，不是靠前端不顯示。

被排除的欄位

  • derived.untrusted.* —— 抽取出的字串與反編譯碼。 整區刪掉，一個欄位都不留。
  • 字串抽取工具的字串內容（只留 counts）
  • Ghidra 的函式清單與反編譯簽章
  • YARA 命中的字串內容（只留規則名與命中條數）
  • C2 的未 defang 形式（value / host）
  • 分析機的絕對路徑（meta.source_path、各工具的 argv）

動態端（mirage）另外排除

  • 模擬期間掃到的記憶體字串與我方注入的字串
  • 樣本傳給 API 的字串引數的值 —— 檔名、帳號密碼、C2 都在裡面。 只留 API 名稱
  • 逐指令軌跡與那些位址上的原始位元組（那是樣本的機器碼）
  • 例外的 traceback（含分析機的原始碼路徑與行號）
  • 模擬器裡的完整檔案路徑與以 sha256 命名的模組區段名

為什麼要整區排除

樣本作者可以控制自己 binary 裡的字串與程式碼。那些內容可能夾帶第三方情報、 受害者資料，或針對讀報告的 LLM 寫的注入指令。 原始 schema 已經刻意把它們集中在一個欄位底下就是為了這件事 —— 消費端只要整個丟掉就安全。

腳本用白名單複製欄位，而不是黑名單刪除。寫檔前它會自己掃一次輸出： 黑名單欄位、明文 URL scheme、Windows／Unix 絕對路徑、看起來像憑證的字串 —— 出現任何一個就中止，而且不寫出任何檔案。

LLM 的診斷文字是模型的輸出，不是樣本內容，所以有收錄； 但它可能複述樣本給它看的字串，所以當成不可信文字處理： 去控制字元、截長度、絕對路徑抹掉、URL scheme defang， 前端一律用 textContent 輸出而不是 innerHTML。

這個站是純 HTML + CSS + 原生 JavaScript，沒有框架、沒有建置步驟、 沒有引用任何外部資源，圖表是手刻 SVG。 以 file:// 直接開啟時 fetch() 會被擋掉， 會自動改讀同一份內容的 data/data.js。

AIS3 專題資料瀏覽頁。純靜態，無外部資源，離線可開。
