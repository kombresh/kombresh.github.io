AIS3 惡意程式分析專題static intel × speakeasy
總覽 方法說明

反分析的樣本，在模擬器裡走得完嗎？

六支真實惡意樣本，先丟進 Speakeasy 直接模擬當基線，再用 LLM 逐輪捏造 API 回傳值把它推下去， 同時用靜態流水線抽出反分析檢測點 —— 看每多花一分力氣，換到多少行為。

三組數據三組都有資料了

這個專題的主軸是「多花的力氣換到多少行為」。三組數據是同一批樣本、逐步加條件的對照： ① 什麼都不做直接丟進模擬器、② ＋動態（LLM 即時捏造 API 回傳值 ＋ 每輪修訂環境剖繪）、 ③ ＋動態＋靜態（靜態報告派生的環境剖繪與模擬預算餵給動態端）。 ③ 和 ① ② 不是同一個批次，所以它自己帶了一組同批的對照 （空 profile ＋ 預設預算），要比就比那兩欄 —— 跨批次比較會把批次差異算成靜態情報的功勞。

樣本點卡片看逐輪圖表

每一支的詳情頁有兩張圖：第一張的橫軸是基線 → mirage 的每一輪，第二張是第三組的 同批對照（normal 與 static-profile 逐輪並排）。縱軸都是那一輪觀察到的 API 呼叫數。 點任一根長條會展開那一輪多了／少了哪些 API、LLM 產出了什麼讓它 能進到下一輪、以及那一輪的結局判定。

跨樣本總覽三組對照並排 · 右半來自靜態分析

① 是純 Speakeasy 基線、② 是 mirage（＋動態）、③ 是 ＋動態＋靜態。 ② 的「每輪 API」是每一輪各自的計數，不是累積；標了「對數」的兩支， 輪與輪之間跨了兩到三個數量級。 ③ 的兩個數字是同一批次裡「空 profile → 靜態派生 profile」的變化， 不能拿去跟 ② 比；而且那一批只套用了 profile 與模擬預算，靜態端同時產出的 建議 watchlist 沒有進場，所以 ③ 是對交接機制的部分驗證。 「檢測點」是靜態端在匯入表／字串裡認出的反分析相關 API 數；「分類」是這些檢測點落在幾個行為類別。 「C2」欄的括號內是非 benign 的筆數 —— 白名單過的 CDN／憑證撤銷清單網域不算。 加殼為「是」的那支，靜態端的欄位是證據不完整的：解不開殼就看不到裡面。

這個站放了什麼、沒放什麼

沒有放進來的東西

  • 樣本本體與任何原始位元組 —— 一個 byte 都沒有
  • 從樣本記憶體／檔案抽出的字串內容（只留條數）
  • 反編譯出來的程式碼與函式簽章
  • YARA 命中的字串內容（只留規則名與命中條數）
  • 可直接點擊的 C2 —— 一律以 hxxp://、[.] 形式呈現
  • 動態端：模擬期間的記憶體字串、樣本傳給 API 的字串引數 （檔名、帳密、C2 都在裡面）、逐指令軌跡與原始位元組 —— 只留 API 名稱與計數
  • 分析機與模擬器裡的絕對路徑

LLM 的診斷文字有收錄，但當成不可信文字處理：路徑抹掉、URL scheme defang、 前端只用 textContent 輸出。

過濾在哪裡做

在 tools/build-data.py，不是靠前端不顯示。那支腳本用白名單複製欄位， 寫檔前會自己掃一次輸出：黑名單欄位或明文 URL scheme 只要出現一個， 就直接中止而且不寫出任何檔案。

理由：樣本作者可以控制自己 binary 裡的字串。那些內容可能夾帶第三方情報、 受害者資料，或針對讀報告的 LLM 寫的注入指令。
